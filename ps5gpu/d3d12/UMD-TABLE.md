# ps5d3d12.dll: the Direct3D 12 driver interface, mapped to vkd3d-proton

Phase 0 of `windows-handoff/WDDM2-DX12-PLAN.md` (decision D2: a thin driver DLL that forwards to vkd3d-proton used as
a library), written 2026-11-23 (Opus). Header: `build/wdk/x-wdk.x64/c/Include/10.0.28000.0/um/d3d12umddi.h`.
The function rows below are generated by `tools/umdtable.py` from that header plus its mapping table.

## Which interface version 19044 negotiates

- The runtime asks the driver's `pfnGetSupportedVersions` for a list of `D3D12DDI_SUPPORTED_xxxx` values and picks one
  it knows, then calls `pfnCreateDevice` with it and asks for each function table by type (`pfnFillDDITable`, with the
  size it expects). documented (header).
- Windows 10 19041.2965 (22H2 ISO; same 19041 code base as LTSC 19044.1288) ships `d3d10warp.dll`, itself a D3D12 driver.
  Its supported-version array (found in the binary, 36 entries): 0003, 0015, 0020-0028, 0030-0034, 0040-0043, 0050-0054,
  0060-0065, 0072-0076. `D3D12Core.dll`'s public symbols show a DDI version enum of 40 values. binary.
- The header marks 0070-0076 as "D3D12 Release 7" and everything from 0080 as "Release 8" (Windows 11 / Agility SDK).
  19041 = Release 7. **Target: `D3D12DDI_SUPPORTED_0076` only.** Tables at that version: device core
  `D3D12DDI_DEVICE_FUNCS_CORE_0075`, command list `D3D12DDI_COMMAND_LIST_FUNCS_3D_0074`, queue
  `D3D12DDI_COMMAND_QUEUE_FUNCS_CORE_0001`, DXGI table (size from the runtime, `DXGI1_6_1_DDI_BASE_FUNCTIONS` layout).
  binary + documented. **Confirmed on the console 2026-11-23** (dev Windows 19044, probe driver
  `ps5gpu/d3d12/probe/d3d12probe.c` in the 4th `UserModeDriverName` slot, ps5wddm in 2.0 mode): offered WARP's 36
  versions, Windows' own d3d12.dll chose interface 0x000C0046 / version 0x00060000 = 0076. Before that it asks only
  caps 1007 (3D pipeline level; 0 = adapter rejected with 887A0004, 13 = 12_1 accepted). Still a guess for 1288 (same
  release; DDI builds are not added in servicing). The
  DLL logs the version the runtime chose (phase 3 checks it on 1288). Fallback if 1288 refuses: 0065 (Release 6), whose
  tables are a prefix of the same structures except a few argument structs.
- Optional tables (`pfnGetOptionalDDITables`): none. Without the render-pass table the runtime emulates render passes;
  no video, content protection, meta commands, shader-cache funcs.

## Shape of the layer

- One `P5Device` per runtime device: a vkd3d-proton `ID3D12Device` created on our RADV (libps5gpu) through vkd3d's
  `vkd3d_create_device` with the DXGI parts unused. Every DDI handle points at driver-private memory the runtime sized
  with our `pfnCalcPrivate*Size`; we keep a COM pointer (and for decomposed objects, the descriptions) in it.
- Descriptors: the runtime does handle arithmetic with our increment size and our heap start, so vkd3d's CPU/GPU handles
  pass straight through.
- GPU virtual addresses programs see are vkd3d's (from `pfnCheckResourceVirtualAddress`), not Windows'. Windows' GPU VA
  space (WDDM 2.0 page tables) only holds fences and the few Windows allocations.
- Memory: vkd3d allocates through RADV -> ps5gpu.sys (p5core). Windows allocations (`pfnAllocateCb`) only for swap-chain
  buffers and resources shared with other processes. `MakeResident`/`Evict`/`Offer`/`Reclaim` are no-ops.
- One queue thread per command queue keeps the runtime's order of Execute / Signal / Wait / Present.
- Presents: swap-chain buffers are Windows allocations in our segment (as the Direct3D 10 driver's). Phase 3: the picture
  is copied into them the same way the D3D10 driver does today (map + CPU copy, `LockCb`), then `pfnPresent` returns the
  allocations and a physical kernel context; the runtime presents, `DxgkDdiPresent` copies to the screen. Copying on the
  GPU (import of the segment's memory into RADV) is a phase 4 speed item.

## Hard list (everything else is a direct call or kept state)

1. **Shader bytecode.** `pfnCreate*Shader` gets the program (`pShaderCode`, length in `pShaderCode[1]`) and its I/O
   signatures as arrays of {system value, register, mask, component type} with **no semantic names**; vkd3d-proton
   expects a full shader container. DXBC: build a container with SHEX = the tokens and ISGN/OSGN/PCSG from the arrays,
   names synthesized (system values get their SV_ name, others `P5IN`/`P5OUT` with index = register); stage linking in
   vkd3d-shader is by register (guess, to check). DXIL (SM 6.x): the program is the DXIL part; its signatures are inside
   the module's metadata, so a container with the DXIL chunk (plus signature chunks built the same way) should do (guess).
   The input layout (`pfnCreateElementLayout`, by `InputRegister`) uses the same synthesized names.
2. **Fences.** The runtime gives only the Windows fence's GPU virtual addresses. Signal = our queue thread waits for
   vkd3d's private fence, then submits an `OP_FENCE` DMA buffer on a virtual kernel context; ps5wddm writes the value
   through its page-table walker and completes the submission. Wait = poll the value through escape `P5E_FENCE_READ`.
   (Kernel side: `ps5gpu/wddm/WDDM2-TABLE.md`, "Fences".)
3. **Present** (`pfnPresent`): Windows allocation behind each swap-chain buffer, copy, return src/dst handles and contexts.
4. **Opened shared resources** (`pfnOpenHeapAndResource`): only our own allocations (they carry `P5AllocData`); anything
   made by another driver/API is refused.
5. **Raytracing state objects** (`pfnCreateStateObject`, `pfnAddToStateObject`): DDI subobjects back to
   `D3D12_STATE_OBJECT_DESC`. Off (caps report no DXR) until phases 3-4 pass.
6. **Pipeline state re-assembly** (kept state, listed because it is the biggest of them): the DDI decomposes a PSO into
   shader, blend, depth, rasterizer and element-layout objects; `pfnCreatePipelineState` rebuilds the API description.

No class of calls lacks an API equivalent: the thin layer can work (plan's phase 0 exit). Root signatures come parsed
and are re-serialized with vkd3d's serializer (kept state, not hard).

## Callbacks the layer uses (D3D12DDI_CORELAYER_DEVICECALLBACKS_0050)

`pfnSetErrorCb`, `pfnSetCommandListErrorCb`, `pfnCreateContextCb` (present context, physical),
`pfnCreateContextVirtualCb` (fence-write context), `pfnAllocateCb`/`pfnDeallocateCb` (swap-chain/shared allocations);
the D3DKMT thunks (`D3DKMTLock2`, `D3DKMTEscape`, `D3DKMTSubmitCommand`) are called directly, as Windows' own D3D12
drivers do. Not used: paging queues, `MakeResidentCb`, hardware queues, scheduling-group contexts.

## Tables at 0076

Kinds: **trivial** = direct call or constant; **state** = keeps or rebuilds a description; **stub** = not reached when
the caps say so, or a harmless answer; **hard** = in the hard list.
